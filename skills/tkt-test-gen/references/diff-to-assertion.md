# diff → 影响面 → 断言:生成用例的方法论

把一次代码改动转成能抓住回归的视觉断言,核心是三步:提炼「用户可见变化」→ 判断影响面 → 写出对应断言。视觉回归测的是渲染结果,不是代码本身。

## 1. 提炼「用户可见的变化」

读 diff 时,只关心「用户打开页面后,哪里不一样了」。三类变化:

| 改动类型 | diff 里看什么 | 用户可见的变化 |
| --- | --- | --- |
| 样式(z-index / 溢出 / 对比度) | CSS / 内联样式 | 遮挡、裁切、可读性 |
| 交互(点击 / 跳转 / 表单) | 事件处理 / 路由 | 行为、状态切换、跳转结果 |
| 结构(组件 / 布局) | 模板 / JSX | 元素增删、排列变化 |

**反例**:纯重构(变量改名、函数抽离)、不影响渲染的改动 → 不生成视觉断言。代码内部实现变了但渲染结果没变,视觉回归测不出来,也别硬测。

## 2. 判断影响面

改了一个组件/样式,要问「哪些页面用到了它」。判断路径:

1. 改动文件对应哪个页面/组件(从路径和 import 关系判断)
2. 这个组件被哪些页面引用(全局组件影响面大,局部组件影响面小)
3. 每个受影响页面 = 一个潜在回归点

影响面判断不准时,**读项目现状或问用户**,不猜。

## 3. 断言写法:确定性 vs 视觉

e2e/ 的 fixture 同时提供两种断言,分层用:

| 分层 | 断言方式 | 何时用 | 成本 |
| --- | --- | --- | --- |
| **P0** | `expect(locator).toBeVisible()` 等确定性断言 | 变化能被「元素存在/可见/文案」确定地抓到;不依赖后端/登录 | 免费快,每次提交都跑 |
| **P1** | `aiAssert('自然语言')` | 变化需要「视觉判断」(遮挡/裁切/可读性/布局),确定性断言抓不到 | 调多模态模型,有成本 |

**关键判断**:这个变化是「确定性能断言」还是「必须靠视觉」?

- 加了按钮 → `expect(button).toBeVisible()` 够(P0)
- 改了 z-index 防遮挡 → 只能 `aiAssert('面板不被遮挡')`(P1,遮挡是视觉概念)

## 4. 断言要「抓住回归点」

每条断言的措辞要对应 diff 里的具体变化,不是泛泛的「页面正常」:

| 改动 | 坏断言(通用) | 好断言(抓回归点) |
| --- | --- | --- |
| 改 z-index 防遮挡 | 「面板正常显示」 | 「筛选面板展开时不被其他元素遮挡」 |
| 改溢出 | 「表格正常」 | 「超长邮箱不把操作列挤出屏幕」 |
| 改暗色对比度 | 「页面正常」 | 「暗色模式下文字清晰可读,对比度足够」 |

## 5. 完整示例

diff 改了筛选面板 z-index:

```diff
- .filter-panel { z-index: 10; }
+ .filter-panel { z-index: 100; }
```

生成草稿:

```
用例名: 更多筛选面板不该被其他元素遮挡
防回归: z-index 从 10 改 100,防面板展开时被其他元素盖住
分层: P1(遮挡是视觉概念,必须 aiAssert)
断言: aiAssert('筛选面板展开时,面板内容完整可见,不被其他元素遮挡')
group: 布局  /  desc: z-index 层级,回归高发区
```

写回 cases.json 对应条目:

```json
{
  "更多筛选面板不该被其他元素遮挡": {
    "group": "布局",
    "priority": "P1",
    "desc": "z-index 层级,回归高发区"
  }
}
```

## 6. 分层判断速查

- **P0 确定性**:变化 = 元素增删/可见/文案,`expect(locator)` 能抓到 → 免费,进提交冒烟集
- **P1 视觉**:变化 = 遮挡/裁切/可读性/布局/交互结果,必须 `aiAssert` → 调模型,进全量回归
- 拿不准分 P0 还是 P1,问「`expect(locator)` 能确定地抓到吗」,能则 P0,不能则 P1
