# tkt-walkthrough

实现完一组功能后的**自动回归走查**:派子 agent(独立上下文)用 agent-browser 像用户一样把功能走一遍,回来交「问题清单」,主 agent 修;修完复走查一次,直到无实质问题。

IRON LAW:
- **派子 agent 必附「上下文注入块」**(见 Workflow-2):登录/URL/后端现状/已知坑/被测文件路径/清理纪律,否则子 agent 会重复摸索登录与结构,浪费一轮。上下文是主 agent 的责任,不是子 agent 的探索任务。
- **问题清单每条必含**:复现步骤 → 现象(原样文本/截图路径)→ 期望 → 根因方向。禁止「有问题」这种空话。
- **修完必复走查**:至少对修复项回归一轮;不修就收尾,等于没走查。
- 后端/数据问题不当前端硬修;拿不准先「直调接口复核」再定性。

## Workflow

```
tkt-walkthrough Progress:

- [ ] Step 1: 定范围 ⚠️ REQUIRED
  - [ ] 1.1 锁本轮走查的功能面(这次实现/改了什么 + 用户点名项)
  - [ ] 1.2 盘点后端接口现状与已知坑(git diff + 接口文档,先自查,别让子 agent 重查)
- [ ] Step 2: 组上下文注入块 ⛔ BLOCKING
  - [ ] 2.1 填清 登录/URL/路由/后端数据/已知背景/清理纪律/文件路径(模板见下)
- [ ] Step 3: 派子 agent 走查 ⚠️ REQUIRED
  - [ ] 3.1 prompt = 上下文注入块 + 逐项走查指令 + 输出格式要求
  - [ ] 3.2 只读优先;确需新建测试数据 → 明令它走查完自删清场
  - [ ] 3.3 截图落 /tmp 作证据(主 agent 需要时再读,不强制全读图)
- [ ] Step 4: 收清单 → 定性分类 ⚠️ REQUIRED
  - [ ] 4.1 前端可修 → 直接修
  - [ ] 4.2 后端契约/数据问题 → 直调接口复核后转交(注明谁/接口)
  - [ ] 4.3 需要用户定夺 → 单独列出等用户
- [ ] Step 5: 修复 + 复走查 ⛔ BLOCKING(有修复时)
  - [ ] 5.1 改完 lint/编译过
  - [ ] 5.2 对修复项复走查(轻量可主 agent 自己查,重回归再派子 agent)
- [ ] Step 6: 汇报 ⚠️ REQUIRED
  - [ ] 6.1 清单表:# 问题/归属/处理/状态
  - [ ] 6.2 后端遗留项单列(等后端改/等接口)
```

## Step 1: 定范围

先自己扫一遍差异:git status/diff 清单、上一轮实现面、用户点名的重点(如「状态切换不对劲」→ 把它列为显式走查项)。后端接口现状/已知坑**先自查**(接口文档、直调过的手感),避免子 agent 重探。

## Step 2: 上下文注入块(必填模板)

派子 agent 前把这块填好粘进 prompt。**子 agent 只做功能走查,不负责发现这些**:

```
## 上下文(已核实,直接用)
- 应用/URL: http://localhost:8899(dev,已起)
- 登录: open /testlogin.html → 选账号「杨浩然」→ 若到身份选择页点「应用管理员」→ 进管理端
- 被测路由: /#/manual/list(管理端手册列表) 与 /#/manual/edit/{code}?code={code}(编辑)
- 后端: 真实接口 manual-full 系列(list/detail/create/update/status/sort/delete),base 前缀 /online-manual 已去
- 后端数据现状: 现有 N 本手册(标题列表/status),其中 X 本 content 异常(…)
- 已知背景: 例如 detail 返回 content 空、/sort /status 会刷 updatedAt —— 复核时勿当新发现,而是确认/补充
- 被测源码: web/src/pages/manual/{list,edit}.vue、web/src/api/manual.ts
- SPA 导航: 用 agent-browser eval 切页,别 open 受保护页;操作先 snapshot -i 拿真实 ref,禁止猜 DOM
- 清理纪律: 走查只读优先;确需新建/改状态,记录原值并还原,自建数据走查完自删;勿动他人数据
```

## Step 3: 派子 agent 走查

prompt 结构:上下文注入块 → 走查项(逐条「操作→期望看到什么」,用户点名的放最前)→ 输出格式(问题清单每条=复现/现象/期望/根因方向,正常项写「通过」)→ 约束(只读、别改源码、截图留证据路径)。

子 agent 类型:general-purpose(自带 Bash;agent-browser 已在环境)。后台跑,收通知。

## Step 4: 收清单定性

子 agent 的「根因方向」是建议不是结论——主 agent 对每条**亲自复核**再动手:
- 前端 bug → 读代码确认后修
- 疑似后端(字段空/排序被忽略/接口行为)→ 先用 eval fetch 直调接口复核,拿实锤;真后端问题**不要硬在前端补**,转交后端(注明接口/现象/期望),前端仅加不误导的保护提示(可选)

## Step 5: 修复 + 复走查

修复按类型合并改,lint/编译必须过。复走查:轻量修复(单点绑定/文案)→ 主 agent 浏览器/DOM 直接验;全量回归/多处 → 再派子 agent 走查「只查上轮清单项」,确认 closed。

## Anti-Patterns

- 子 agent prompt 不给上下文,让它自己找登录/后端现状(浪费一轮 + 可能踩错环境)
- 子 agent 走查时乱建数据不清理/改他人数据状态(上下架/排序会刷 updatedAt——注入块明令还原)
- 主 agent 把问题清单当结论直接照抄,不复核(子 agent 可能定性错)
- 后端/数据问题在前端硬造补丁(该转后端就转,前端最多加提示)
- 修完不复走查就宣称完成
- 走查发现全空(应追问:范围够不够/子 agent 是否真操作了,不轻信「全部正常」)

## Pre-Delivery Checklist

- [ ] 派子 agent 前上下文注入块已填(登录/路由/后端现状/清理纪律/文件路径)
- [ ] 子 agent 走查产生的问题清单逐条有 复现/现象/期望/根因
- [ ] 主 agent 已逐条复核并分类(前端修/后端转交/待用户)
- [ ] 修复项已复走查/回归验证,lint 过
- [ ] 后端遗留项已单独列出转交,数据副作用已还原或说明
